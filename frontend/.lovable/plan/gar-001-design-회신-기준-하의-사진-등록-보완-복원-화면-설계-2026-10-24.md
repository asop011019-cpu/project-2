## 1. 화면 구성 (한 화면, `/`)

모바일 (360~430px, 세로 1열)
```text
[작은 상단 라벨: "STEP 01 · 기준 하의"]  (브랜드명은 넣지 않음)
[큰 제목: "코디의 기준이 될 하의 한 벌"]
[대형 사진 영역 3:4, 화면 폭 전체]
   - 비었을 때: 얇은 테두리와 안내 문구, [사진 선택] [촬영하기]
   - 사진이 있을 때: 사진 + 우하단 텍스트 버튼 [교체] [삭제]
[종류 *  ( 바지 | 치마 )  세그먼트, 필수]
[선택 입력] 브랜드 / 제품명 / 구매처 링크
[상태 한 줄: "사진과 정보가 저장됨" 등]
[하단 고정 버튼: 저장하기]
```
데스크톱 (1024px 이상): 2열입니다. 왼쪽 7/12에 사진을 sticky로 두고, 오른쪽 5/12에 제목, 입력 칸, 저장 버튼을 둡니다. 최대 폭은 1200px입니다.

톤: 밝은 웜 오프화이트 배경, 먹색 글씨, 세리프 디스플레이 제목과 산세리프 본문 조합(예: Noto Serif KR + Pretendard), 얇은 구분선을 씁니다. 모션은 사진 페이드 정도만 둡니다. 상품 그리드, 샘플 상품, 생성 이미지는 쓰지 않습니다.

입력 방식
- `<input type="file" accept="image/jpeg,image/png,image/webp">`로 사진을 선택합니다.
- 촬영은 같은 input에 `capture="environment"`를 붙인 두 번째 버튼으로 엽니다. 데스크톱에서는 이 버튼을 숨깁니다.

## 2. 상태 흐름

```text
복원중 --GET 200 null--> 빈 상태
복원중 --GET 200 garment--> 저장완료(복원)
빈 상태 --파일선택--> 사진읽는중 --실패--> 형식실패 (기존 사진/입력 유지)
                         --성공--> 미저장 편집
미저장 편집 --저장--> 저장중 --200--> 저장완료
                     --오류--> 실패/재시도 (입력·로컬사진 유지)
저장완료 --정보만 수정--> 미저장 편집 (image 파트 생략)
저장완료 --교체--> 사진읽는중 ... (image 첨부)
저장완료 --삭제 확인--> 삭제중 --204--> 빈 상태 / 실패 시 기존 유지
```
- 복원중: 사진 영역에 스켈레톤을 표시하고 버튼은 비활성화합니다.
- 사진읽는중: 클라이언트에서 형식, 10MiB 이하인지, 이미지 디코드 가능 여부를 먼저 확인합니다(`createImageBitmap` 또는 `Image`). 미리보기는 objectURL로 보여주고 해제 처리합니다.
- 형식실패 문구는 원인별로 다르게 씁니다.
  - HEIC: "아이폰 HEIC 사진은 아직 지원하지 않아요. 설정 > 카메라 > 포맷 > '높은 호환성'으로 찍거나 JPG로 저장해 주세요."
  - 용량 초과: "10MB 이하 사진만 올릴 수 있어요."
  - 손상: "사진을 열 수 없어요. 다른 사진을 골라 주세요."
- 저장중: 버튼을 "저장 중…"으로 바꾸고 중복 제출을 막습니다. 입력 칸은 읽기 전용으로 둡니다.
- 실패/재시도: 코드별 문구를 보여주고 [다시 시도] 버튼을 둡니다. 413/415/400은 백엔드 message를 우선 쓰고, `issues`는 해당 필드 아래에 표시합니다. 401은 세션을 재생성한 뒤 1회 자동 재시도하고, 그래도 실패하면 안내합니다. 403/500은 일반 안내와 함께 requestId를 작게 표시합니다.
- 저장완료 문구: "사진과 정보가 저장되었어요"까지만 씁니다. 분석이나 추천이 끝났다는 표현은 쓰지 않습니다.
- 새로고침복원: 로드 시 `POST session` 후 `GET garment`를 호출합니다. 사진은 `/api/onboarding/session/garment/image?v=updatedAt`으로 불러옵니다.
- 삭제: 확인 다이얼로그 "등록한 하의를 삭제할까요?"를 거친 뒤 204를 받으면 빈 상태로 돌아갑니다.
- 저장 버튼 활성 조건: 사진(로컬 또는 저장본)이 있고 종류가 선택되어 있으며 변경 사항이 있을 때입니다.

## 3. API 계약 추가 확인 필요

1. 백엔드 주소와 프록시: 이 프론트(Cloudflare Worker로 배포)에서 같은 출처로 `/api/*`를 어떻게 넘길지 정해야 합니다. 후보는 Worker 서버 라우트 프록시와 상위 리버스 프록시입니다. 쿠키 도메인과 SameSite 조건도 함께 확인이 필요합니다.
2. `GET garment`에도 세션 선행이 필요한지 확인해야 합니다. 세션이 없을 때 401인지 `{garment:null}`인지도 정해야 합니다.
3. `X-Onboarding-Request: 1`을 GET에도 붙여야 하는지, 변경 요청(PUT/DELETE/POST)에만 붙이는지 확인해야 합니다.
4. imageUrl 형식(상대경로 여부)과 캐시 무효화 방식(`updatedAt` 쿼리 허용 여부, ETag)을 확인해야 합니다.
5. width/height가 원본 기준인지, EXIF 회전 반영 후 값인지 확인해야 합니다.
6. 최초 PUT에서 image가 없을 때의 code 값, metadata JSON 파싱 실패 시의 code 값이 필요합니다.
7. purchaseUrl 검증 규칙(https만 허용하는지, 최대 길이)과 brand/productName 최대 길이를 알려주시면 클라이언트 표시를 맞추겠습니다.
8. 413이 프록시 단계에서 HTML로 올 때 대비가 필요합니다. 클라이언트는 JSON이 아닌 응답도 처리하겠습니다.
9. 동시 수정 충돌(두 탭) 처리가 필요한지 확인해야 합니다. 현재 설계는 마지막 저장이 우선합니다.
10. DELETE 시 이미지 파일도 즉시 삭제되는지 확인해야 합니다. 이건 문구 정확성을 위한 확인입니다.

- `src/routes/index.tsx`: 화면 전체, head 메타 포함
- `src/components/garment/GarmentPhoto.tsx`, `GarmentForm.tsx`: 2~3개 컴포넌트
- `src/lib/onboarding-api.ts`: fetch 래퍼(credentials include, 헤더, 오류 파싱), 세션 토큰 저장 없음
- `src/lib/image-check.ts`와 테스트: 형식, 용량, HEIC 판별 규칙
- `src/styles.css`: 색상, 폰트 토큰
- `src/routes/__root.tsx`: 폰트 link, Toaster, lang="ko"
- 프록시 방식이 확정되면 `src/routes/api/...` 프록시 1개를 둡니다. 확정 전에는 만들지 않습니다.

상태 관리는 React Query(`useQuery` 복원, `useMutation` 저장/삭제)와 로컬 useState만 씁니다. 추가 라이브러리, 가짜 API, 새 DB는 도입하지 않습니다. API가 미연결인 동안 화면은 "서버 연결 대기" 오류 상태로 정직하게 표시됩니다.
