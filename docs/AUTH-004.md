# AUTH-004 회원 탈퇴 백엔드

- 브랜치 `feature/auth-002-kakao`(AUTH-002 위에 이어서). 설계: `docs/AUTH-001.md` 9-1장. 사용자 지시("남은 일 진행")로 착수, 화면은 AUTH-003.
- 계약: `DELETE /api/auth/account` (본문 `{}`, `X-Onboarding-Request: 1`). 최근 로그인(기본 10분, `reauthWindowSeconds`)이 아니면 401 `REAUTH_REQUIRED` → `GET /api/auth/kakao/start?reauth=1&returnTo=…`(카카오에 `prompt=login`, 비밀번호 재입력)로 다시 로그인 후 재시도. 성공 204 + 로그인 쿠키 삭제.

## 삭제 순서 (재시도 가능)
1. 한 트랜잭션: 계정 `status=deleting`(새 로그인은 `/login?error=ACCOUNT_UNAVAILABLE`), 계정의 로그인 세션 전부 폐기, 삭제 작업 행(`account_deletions`: 카카오 회원번호·단계·시도 횟수·마지막 오류) 기록. 마이그레이션 v5.
2. 하의 사진 파일과 취향·하의 행 삭제(기존 onboarding 삭제 경로 재사용, 이미 없는 파일은 삭제된 것으로 봄 — 탈퇴 경로에서만). 실패하면 작업 행에 오류만 남기고 계정은 잠긴 채 유지.
3. 계정 행 삭제(로그인 수단·세션·동의·동의 이력은 함께 삭제).
4. 카카오 연결 끊기(`POST kapi.kakao.com/v1/user/unlink`, Admin 키 필요). 성공(또는 이미 끊김 -101)하면 작업 행에서 회원번호를 지우고 `done`.
- 남은 작업은 서버 시작 시와 새 탈퇴 요청 때 자동 재개(로그인 불필요). 같은 카카오로 다시 오면 3단계 이후엔 신규 가입.
- Admin 키(`KAKAO_ADMIN_KEY`)가 없으면 2·3단계(개인 데이터 삭제)는 끝나고, 4단계만 `KAKAO_UNLINK_NOT_CONFIGURED`로 대기하며 회원번호만 남김. 키를 넣고 서버를 재시작하면 마무리됨.

## 실제 카카오 연결 끊기 확인 (2026-10-27)
- 사용자가 `KAKAO_ADMIN_KEY`를 worktree `backend/.env`에 직접 입력(값 미기록). 백엔드(`localhost:3095`, `backend/data/kakao-live`) 재시작 → 시작 시 재개로 대기 중이던 탈퇴 작업이 `data_deleted` → `done`, 회원번호·provider 삭제. 카카오 Admin API `GET /v2/user/me?target_id=…`는 `-101`(앱과 연결되지 않은 사용자)로 실제 연결 끊김 확인.
- 발견한 결함과 수정: 연결 끊기가 Admin 키를 기다리는 사이 같은 카카오 회원이 **다시 가입**해 있으면, 늦게 실행된 연결 끊기가 새 계정의 카카오 연결까지 끊음(이번 실검증에서 실제로 발생 — 데이터 손실은 없고 다음 로그인 때 카카오 동의가 다시 뜨는 정도). 수정: 같은 회원번호의 활성 로그인 수단이 있으면 연결 끊기를 건너뛰고 작업만 `done`으로 정리. 테스트 추가(가드를 제거하면 실패), `npm test` 51개 중 50 통과(기존 symlink 1).

## AUTH-004-R1 실패·재시도·재가입 경합 (2026-10-27, 가짜 카카오만 사용)
### 재가입 경합
- 재현: 연결 끊기 요청이 카카오로 가는 **도중**(이전 수정의 "재가입했으면 생략" 확인 이후)에 같은 회원이 새로 가입하면, 끊기가 새 계정의 카카오 연결을 끊을 수 있음. 가짜 카카오의 unlink를 일시 정지(gate)해 이 순서를 재현함.
- 최소 수정: 연결 끊기 직전 **한 트랜잭션에서** "같은 회원번호의 활성 로그인 수단이 있으면 생략, 없으면 `account_deletions.unlink_started_at` 기록(점유)". 점유가 60초(`unlinkLeaseSeconds`, 카카오 요청 제한 10초보다 긺) 안이면 그 회원의 신규 가입(콜백의 가입 대기 생성과 POST signup의 계정 생성 모두)을 403 `ACCOUNT_UNAVAILABLE`("탈퇴 정리가 끝나는 중이에요. 잠시 후 다시 로그인해 주세요")로 거절. 끊기 실패·키 미설정 시 점유 해제, 서버가 중간에 죽으면 60초 뒤 자동 해제. 마이그레이션 v6(`unlink_started_at`). 기존 화면이 이미 이 오류 코드 문구를 갖고 있어 프론트 변경 없음.
- 외부 제약(보장 불가): 카카오 unlink 요청이 우리 쪽 10초 제한에 걸린 뒤 카카오에서 60초보다 늦게 처리되면, 그 사이 다시 가입한 연결이 끊길 수 있음(다음 로그인 때 카카오 동의 재표시, 데이터 손실 없음). 카카오 API에 조건부 끊기가 없어 서버에서 완전히 막을 수 없음.

### 화면 안내 점검(AUTH-004-R2로 대체)
- 현재 백엔드는 1단계(잠금·세션 폐기·작업 기록)만 끝나면 204를 반환하고, 화면은 204에 "회원 탈퇴가 완료됐어요"를 띄움. 사진·DB 삭제가 실패해 작업이 `pending`이면(개인 데이터가 아직 남음) 이 안내는 부정확. 카카오 끊기만 남은 `data_deleted`는 개인 데이터 삭제가 끝난 상태라 "완료"로 볼 수 있음.
- 호환 제안: 개인 데이터 삭제가 끝났으면 지금처럼 204, 남았으면 202 `{"deletion":{"status":"in_progress"}}`. 현재 프론트 `request()`는 202+JSON도 성공으로 처리해 깨지지 않음(문구는 그대로 "완료"). 이후 Lovable/국소 수정으로 202일 때 "탈퇴를 접수했어요. 남은 정리는 자동으로 마무리돼요" 표시. 합의 전이라 미적용.
- 2026-10-27 사용자 결정(30일 복구 유예)으로 "즉시 완료 + 30일 보관"이 정확한 안내가 되어 202/204 분리는 불필요.

### "30일 후 삭제"를 보장할 수 없는 조건
- 정리 작업 주기: 만료 후 최대 1시간 늦게 삭제(서버가 켜져 있을 때).
- 서버 중단: 다시 시작할 때 삭제.
- 사진·DB 삭제 실패: 1시간마다 재시도, 그동안 계정은 잠긴 채 남음. 사진 삭제 후 DB 단계에서 실패하면 사진만 먼저 지워진 상태일 수 있음.
- 카카오 연결 끊기 실패: 개인 데이터는 삭제됐고 앱 연결만 남음. 재시도, 그 사이 재가입하면 끊기 생략.
- 서버 시계 오류: 시계가 앞서면 일찍, 늦으면 늦게 삭제(역행 시 복구는 보존).
- 여러 서버 동시 실행은 설계 범위 밖(단일 서버·SQLite 전제). 백업 정책이 생기면 백업 속 데이터 보관 기간을 따로 정해야 함.
