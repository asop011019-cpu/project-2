# 장르 분류 데이터·조회 응답 갱신

## 이번 범위

시작 기준은 원격 main 및 `feature/onboarding-backend`의 `35cb710`이며, fetch 후 최신 상태와 미반영 변경 없음을 확인했습니다. 작업 중 추가된 원격 환경 설정 변경 `6afedda`도 fast-forward로 받아 보존했습니다. 저장소에는 백엔드만 있고 기존 온보딩 화면·갤러리·확대·완료 화면 파일은 없습니다. 기존 `project` 앱이나 새 UI를 가져오거나 만들지 않았습니다.

이번 변경은 분류 데이터·조회 응답과 이를 기존 DB에 적용하는 마이그레이션입니다. 상위 장르 복수 선택, 선택 장르로 탐색 필터링, 세션 진행·저장·완료 로직은 구현하거나 바꾸지 않았습니다.

## ID와 기존 데이터 보존

기존 7개 상위 장르 ID를 재사용하고 `men_european_group`, `men_contemporary_group`, `women_contemporary_group`만 추가했습니다. 예를 들어 `men_casual_group`의 표시 이름은 아메리칸이며 `women_other_group`은 스트릿입니다. ID 문자열로 현재 이름을 추측하지 말고 API의 name을 사용합니다.

아래 이름 변경도 새 스타일을 만들지 않고 기존 ID를 유지합니다. 나머지 기존 스타일도 기존 ID를 유지한 채 새 장르로 연결합니다.

| 기존 스타일 ID | 새 표시 이름 |
| --- | --- |
| men_classic | 클래식 테일러드 |
| men_casual | 모던 캐주얼 |
| women_daily_casual | 모던 데일리 |
| women_feminine | 페미닌 |
| women_romantic | 로맨틱·러블리 |
| women_coquette | 코켓 |
| women_preppy | 프레피 |
| women_old_money | 올드머니 |

| women_streetwear | 스트릿웨어 |

스키마 v2 마이그레이션은 기존 스타일의 ID·범주·설명·게시 상태, 모든 이미지 행, 세션·응답·하트·완료 시각·고정 목록을 보존합니다. 운영자가 따로 등록한 알려지지 않은 ID도 삭제하지 않습니다. 새 ID가 다른 범주에 이미 사용 중이면 전체 마이그레이션을 롤백하고 오류로 중단합니다.

원래 코드는 상위 장르 순서와 하위 스타일 순서를 합쳐 탐색 순서를 계산했습니다. 분류만 바꾸면 기존 탐색 순서도 바뀌므로, 직접 연결된 정렬 부분을 분리했습니다. 기존 DB의 실제 정렬(운영자 수정 포함)을 새 exploration_order에 먼저 보존하고, 기존 세션 테이블은 그대로 둡니다.

- `GenreGroup.order`: 상위 장르 안내 순서.
- `Style.order`: 장르 안의 하위 스타일 안내 순서.
- `Style.explorationOrder`: 이번 분류 변경으로 탐색 순서가 달라지지 않게 보존한 정렬값.
- 실제 UI 진행 순서는 여전히 `SessionView.activeStyleOrder`이며 새 분류 순서로 재정렬하지 않습니다.

## 조회 계약

경로는 그대로입니다.

- `GET /api/onboarding/catalog?categoryId=menswear`
- `GET /api/onboarding/catalog?categoryId=womenswear`
- `GET /api/onboarding/styles/:styleId` (게시 조건 유지)

`genreGroups`에 styleDefinitions·준비 상태·사용 가능 수·대표 이미지를 추가했습니다. 다음은 실제 초기 데이터의 남성복 포멀 항목과 같은 구조입니다.

```json
{
  "id": "men_formal_group",
  "categoryId": "menswear",
  "name": "포멀",
  "description": "재킷과 단정한 바지로 격식을 갖추거나 일상에 깔끔함을 더해요.",
  "order": 10,
  "styleDefinitions": [
    { "id": "men_classic", "name": "클래식 테일러드", "order": 10, "contentStatus": "not_ready" },
    { "id": "men_modern_formal", "name": "모던 포멀", "order": 20, "contentStatus": "not_ready" },
    { "id": "men_business_casual", "name": "비즈니스 캐주얼", "order": 30, "contentStatus": "not_ready" }
  ],
  "availableStyleCount": 0,
  "contentStatus": "not_ready",
  "representativeImage": null
}
```

styleDefinitions는 분류 안내용 ID·이름·순서·준비 여부뿐입니다. 초안의 실제 이미지·설명이나 철회된 이미지 URL을 노출하지 않습니다. 게시·사용 권한 조건은 유지합니다. 후속 사진 중심 온보딩에서는 승인된 이미지 1장 이상인 부분 세트도 공개하며 목표 수량은 4–6장입니다. 하위 이름만으로 탐색 가능하다고 판단하지 않습니다. 준비된 이미지가 있을 때만 representativeImage를 제공합니다. 장르 진행 확장은 [현재 API 계약](API.md)을 따릅니다.

## 적용·검증

backend/에서 `npm run db:migrate`를 실행하거나 서버를 재시작하면 기존 DB에도 적용됩니다. 신규 DB는 `npm run db:seed` 또는 서버 시작으로 54개 초안을 등록합니다. DB 초기화·삭제나 의존성 갱신은 필요하지 않습니다. 입력 JSON의 explorationOrder가 생략되면 기존 스타일의 탐색 순서는 유지하며 새 스타일은 뒤에 배치합니다.

`npm run check`, `npm run build`와 통합 테스트 30개로 다음을 확인했습니다.

- 범주별 정확한 5개 장르와 제공된 24/30개 하위 스타일의 이름·소속·분류 순서.
- 초안의 분류 이름 안내와 실제 탐색 콘텐츠·이미지 게시 조건 분리.
- 승인된 대표 이미지 조회 및 기존 탐색 순서 유지.
- v1 DB에서 기존 모든 ID·이미지·응답·하트·완료·현재 위치·고정 목록 보존.
- 운영자 정렬 수정 보존, 재실행 멱등성, ID 충돌 시 스키마·데이터 전체 롤백.
- 기존 저장·복원·권한·응답·완료·서버 재시작 검증 유지.

새 테스트의 v1 JSON fixture는 기존 커밋 35cb710의 분류 스냅샷이며 운영 데이터로 사용하지 않습니다. 화면이 없으므로 실제 브라우저 UI 검증은 수행하지 않았습니다. 실제 이미지도 0장입니다.

## 다음 작업과 누락 계약

상위 장르 선택 UI 및 복수 선택의 저장·복원 API, 전체 탐색/선택 장르 탐색 모드, 선택 장르 변경 시 세션 목록을 어떻게 갱신할지에 대한 계약이 아직 없습니다. 이것들은 이번 분류 조회와 구별해 다음 작업에서 구현해야 합니다. 현재 API에 없는 selectedGenreGroupIds를 프런트엔드가 이미 저장되는 값처럼 표시해서는 안 됩니다.

전체 54개 스타일의 목표 4–6장을 갖추려면 실제 의복 조합 이미지 216–324장과 권한·출처·형식·크기 등록이 필요합니다. 부분 게시와 현재 장르 방문 계약은 API.md의 후속 사진 탐색 규칙을 따릅니다.
